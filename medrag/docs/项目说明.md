# DocRAG Agent 项目说明

## 1. 项目定位

DocRAG Agent 是一个面向 PDF 文献阅读的 RAG 智能助手，主要用于学术论文、技术文档、课程资料、项目报告和政策文件等内容的辅助阅读。

系统把 PDF 原文解析为带页码的文本块，通过向量检索和重排选择与问题相关的证据，再让大模型基于证据生成回答并返回引用来源。项目强调检索过程可调试、回答可追溯、历史可恢复和效果可评估。

本项目不是医学诊断系统。医学文献只是可选测试场景，系统输出不构成医学或其他专业建议。

## 2. 已实现功能

### 2.1 PDF 解析与索引

1. 接收 PDF 上传并校验文件类型。
2. 根据文件内容计算 SHA-256 `document_hash`。
3. 使用 `user_id + document_hash` 判断当前用户是否已上传相同文件。
4. 已索引文档直接返回原 `document_id` 和关联历史会话。
5. 使用 PyMuPDF 按页提取文本并保留页码。
6. 对低文本量页面按配置执行 Tesseract OCR。
7. 使用 `chunk_size` 和 `chunk_overlap` 切分文本。
8. 为 chunk 保存 `user_id`、`document_id`、`page_number` 和 `chunk_index`。
9. 使用 BGE Embedding 生成向量并写入 Chroma。

`document_id` 是数据库中的文档资源标识；`document_hash` 用于识别相同文件。二者职责不同。

### 2.2 检索与重排

普通问答流程先扩大向量召回候选数，再使用 CrossEncoder 对 `query + chunk` 计算相关性并保留最终 top-k。

检索时同时使用：

- `user_id`：限定当前用户。
- `document_id`：限定当前文档。

只使用 `document_id` 无法证明文档属于当前用户。

总结任务使用独立的 Summary Multi-Query 流程：

1. 使用原问题召回 seed chunks。
2. 根据 seed chunks 生成最多 4 个总结子查询。
3. 每个子查询分别向量召回和 Rerank。
4. 按 `document_id + chunk_index` 去重。
5. 统一重排。
6. 限制同一页最多保留的 chunk 数量。
7. 选取最多 12 个片段作为总结上下文。

子查询生成失败时回退原始查询，不阻断主链路。

### 2.3 用户、文档和会话

系统当前采用轻量用户方案：

1. 用户输入 username，并选择默认 `user_type`。
2. 后端创建或获取用户。
3. 前端只在 localStorage 保存当前 `user_id` 和用户显示信息。
4. 文档和会话数据以后端 MongoDB 为准。
5. 切换用户后，只查询该用户关联的数据。

这是逻辑隔离，不是真实鉴权。当前请求中的 `user_id` 可以由客户端伪造，正式多用户系统仍需要登录态、JWT 或 Session。

### 2.4 多轮记忆与 Query Rewrite

每个 conversation 绑定一个用户和一个文档。提问时：

1. 校验 conversation 存在且属于当前 `user_id`。
2. 保存用户原始问题。
3. 读取最近 `history_limit` 条消息。
4. 根据历史和文档语言执行 Query Rewrite。
5. 使用 `rewritten_query` 检索。
6. 使用原始 query 展示和组装最终回答意图。
7. 保存 assistant 回答、sources、rewritten_query、retrieval_queries 和 task_type。

Query Rewrite 只用于检索，不替代用户原始问题。调用失败时回退原始 query。

### 2.5 用户类型

支持以下用户类型：

- `undergraduate`
- `graduate_student`
- `researcher`
- `developer`
- `teacher`
- `general`

优先级为：

```text
本次请求 user_type
  > conversation.user_type
  > user.default_user_type
  > general
```

`user_type` 只控制回答风格、术语密度和侧重点，不能改变事实依据。回答事实仍必须来自检索 sources。

### 2.6 Agent Router

当前 Router 是可解释的规则路由：

- `summary`：总结、摘要、概括、归纳。
- `report`：阅读报告、分析这篇文献。
- `qa`：其他问题。

当前尚未实现复杂多 Agent、自主规划、工具循环或 LLM Router。项目采用单 Agent/工作流式编排，避免为展示概念引入不必要复杂度。

## 3. 分层设计

### Router

负责：

- 接收 HTTP 参数和请求体。
- 调用 Service。
- 将业务异常转换成 HTTP 状态码。
- 返回稳定响应结构。

Router 不直接访问 MongoDB、Chroma 或大模型供应商。

### Service

负责：

- 用户、文档、会话和消息业务规则。
- PDF 处理编排。
- Query Rewrite、检索和任务路由。
- Prompt 组装。
- LLM 调用与异常封装。

### Store

负责：

- MongoDB 连接生命周期。
- users、documents、conversations、messages 集合读写。
- 索引创建和数据库原始文档返回。

Store 不判断 HTTP 状态码，也不负责业务响应格式。

## 4. 数据结构

### users

| 字段 | 说明 |
| --- | --- |
| `_id` | user_id |
| `username` | 用户名，当前用于创建或获取轻量用户 |
| `default_user_type` | 用户默认回答类型 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

### documents

| 字段 | 说明 |
| --- | --- |
| `_id` | document_id |
| `user_id` | 文档所属用户 |
| `document_hash` | PDF 内容 SHA-256 |
| `filename` | 上传文件名 |
| `language` | `zh`、`en` 或 `unknown` |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

MongoDB 使用 `user_id + document_hash` 唯一索引，避免同一用户重复登记相同文件。

### conversations

| 字段 | 说明 |
| --- | --- |
| `_id` | conversation_id |
| `user_id` | 会话所属用户 |
| `document_id` | 会话绑定文档 |
| `title` | 会话标题 |
| `user_type` | 创建会话时的回答类型快照 |
| `created_at` | 创建时间 |
| `updated_at` | 最近消息时间 |

### messages

| 字段 | 说明 |
| --- | --- |
| `_id` | message_id |
| `conversation_id` | 所属会话 |
| `role` | user 或 assistant |
| `content` | 消息正文 |
| `task_type` | qa、summary 或 report |
| `rewritten_query` | 实际检索问题 |
| `retrieval_queries` | Summary Multi-Query 使用的查询列表 |
| `sources` | 当时回答使用的证据 |
| `created_at` | 创建时间 |

保存当时的 sources 而不是重新检索，可以保证历史回答可追溯，并避免索引变化后引用内容发生漂移。

## 5. Prompt 与事实边界

Prompt 分为：

- QA Prompt：围绕当前问题直接回答。
- Summary Prompt：按要求归纳多个文献片段。
- Report Prompt：生成结构化阅读报告。
- Query Rewrite Prompt：补全指代和上下文。
- Summary Query Prompt：生成总结任务的检索子查询。

历史消息用于理解问题，检索片段才是事实依据。如果 sources 为空，系统返回“当前文献未提供相关信息”，不继续调用 LLM。

## 6. 异常与日志

已处理的主要异常包括：

- LLM 超时：504。
- LLM 限流：503。
- LLM 连接失败：503。
- LLM API 异常：502。
- 空回答：502。
- 用户、文档、会话参数错误。
- 文档不属于当前用户。
- Query Rewrite 和 Summary Query 失败回退。

LLM 日志记录 operation、model、耗时、错误类型、状态码和 request_id。当前仍缺少统一 request_id、完整链路耗时和监控指标。

## 7. 测试与评估

业务层 pytest 回归测试当前覆盖：

1. 查询用户全部会话。
2. 拒绝空 document_id。
3. 相同 user_id 和 document_hash 复用文档。
4. Query Rewrite 异常回退。
5. assistant 消息保留 sources。

RAG 小型评估集包含 3 篇公开论文和 15 道问题，覆盖：

- 事实题
- 术语题
- 对比题
- 总结题
- 无答案题
- 多轮追问题

当前保存的旧基线为：

- Execution Success Rate：1.0000
- HitRate@3：0.6667
- Recall@3：0.5972
- MRR@3：0.5417

这组结果早于最近的 Summary Multi-Query 修改，只能作为旧版本基线。评估最新版本时必须重新执行问答请求，而不是只重新运行指标脚本。

## 8. 当前限制

1. 轻量用户模式不具备真实鉴权能力。
2. PDF 文件读取和模型推理尚未完成容量与并发验证。
3. OCR 不等于多模态理解，复杂表格、公式、图表和图片语义仍可能丢失。
4. 本地 Chroma 在免费云实例中不保证长期持久化。
5. `/health` 仅证明 FastAPI 进程存活，不证明依赖全部可用。
6. 自动化测试主要为业务层 Mock 测试，缺少接口和真实依赖集成测试。
7. 评估集规模较小，适合回归，不足以代表生产质量。
