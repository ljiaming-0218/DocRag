# DocRAG 项目说明

## 项目定位

DocRAG 是一个可部署、可评估的多文档 PDF RAG 应用。系统重点是把文档处理、索引生命周期、检索、回答、引用持久化和运行验收连接起来，而不是只展示一次 LLM 调用。

截至 **2026-10-18，本轮 DocRAG Harness 本地演示版已完成收尾**：保留原有 RAG，增加可持续执行、可追溯的单 Agent 研究循环，并完成三题九组真实模型对照。当前工作区尚未发布新的线上版本。旧版 CI、线上部署和 20 题数据保留为基础 RAG 历史证据。

## 已实现能力

### 文档处理与索引

- PDF 按页解析，低文本量页面可选 OCR 回退。
- `fixed` / `recursive` 切片，保留页码、字符范围、策略和版本。
- `document_hash` 去重，`index_fingerprint` 判断索引配置是否变化。
- MongoDB 持久化 ingestion job：创建、查询、失败重试和幂等。
- 独立 `index_generation_id` 写入，验证完成后通过 active generation 切换。
- Embedding 和 Chroma 写入支持批处理。

### 检索与生成

- Dense 基线和 BM25 + RRF Hybrid 检索。
- 扩大候选池后执行 CrossEncoder 全局重排。
- Query Rewrite 支持追问上下文补全，失败时回退原问题。
- Summary Multi-Query 为总结问题生成多个检索子查询。
- `qa`、`summary`、`report`、`term`、`source_check` 任务路由。
- 无证据时拒答，并保存回答来源、改写问题和检索查询。

### 用户、知识库与会话

- Argon2 密码哈希和 JWT 登录。
- 用户、知识库、文档、会话和消息按 `user_id` 做资源归属校验。
- 一个知识库可关联多个文档；会话可选择整个知识库或部分文档。
- 前端展示 ingestion 状态、失败原因、历史会话和可展开 sources。

### 单 Agent Harness

- 模型可选择搜索文档、读取证据、保存研究笔记、提交报告；工具反馈进入下一轮决策。
- 服务端固定用户、知识库、文档和索引 generation，运行层管理工具约束、预算和停止条件。
- 独立 research worker 执行任务，MongoDB 保存任务、步骤和证据检查点，支持租约恢复与取消。
- 新任务默认单次模型请求 600 秒、总时限 5400 秒（含排队），最多 8 次模型请求和 12 次工具执行。已有任务沿用其持久化预算。
- 前端复用输入框与文档选择，过程可折叠、引用可展开；终态报告支持继续研究，沿用原范围与有限上下文，新任务单独计预算。
- 历史会话和研究任务支持删除；运行中研究先取消。研究入口按用户保存在本机浏览器，完整内容由服务端保存，尚无跨设备历史列表。

这套 Harness 是单 Agent 的运行管理能力，前端“深入研究”是它的使用入口，没有更换已有检索栈。

## 关键设计边界

| 问题 | 当前设计 | 取舍 |
| --- | --- | --- |
| 为什么保留 Fixed | 作为可重复的切片基线 | 便于和 Recursive 做单变量比较 |
| 为什么先 Hybrid 再 Rerank | BM25 补精确词，Dense 补语义，Rerank 提升排序精度 | 增加延迟和模型成本，需用评估集校准 |
| 为什么使用 index fingerprint | 切片、Embedding 或索引版本变化时不能盲目复用旧向量 | 需要持久化配置和代次切换 |
| 为什么保存 sources | 历史消息查看时不重新检索 | 索引变化后仍能追溯当时证据 |
| 为什么索引任务返回 202 | 长 PDF 处理不占用单次 HTTP 请求 | ingestion worker 仍在应用进程内；research worker 独立运行 |
| 为什么使用 Harness 循环 | 复杂问题可根据证据缺口继续选工具 | 调用与等待增加，普通事实题仍可使用原有问答 |

## 分层结构

```text
Frontend
  → Routers：HTTP 参数、认证和状态码
  → Services：业务编排、解析、检索、Prompt、LLM
  → Harness：研究循环、工具、任务状态和独立 worker
  → Stores：MongoDB 集合和连接管理
  → External：Chroma、Embedding、Reranker、LLM、Tesseract
```

Router 不直接访问数据库或模型供应商；Service 不把 HTTP 状态码写入持久层；Store 不负责业务决策。

## 主要数据

| 集合 | 关键字段 |
| --- | --- |
| `users` | `user_id`、`username`、`default_user_type` |
| `documents` | `document_id`、`user_id`、`document_hash`、`index_fingerprint`、`active_index_generation_id` |
| `knowledge_bases` | `kb_id`、`user_id`、`name` |
| `conversations` | `conversation_id`、`user_id`、`document_id`、`kb_id`、`selected_document_ids` |
| `research_tasks` | 任务状态、固定范围、预算、parent_task_id、报告和租约 |
| `research_events` | 任务步骤与工具执行事件 |
| `research_evidence` | 任务证据、来源与引用编号 |
| `messages` | `role`、`content`、`task_type`、`rewritten_query`、`retrieval_queries`、`sources` |

MongoDB 保存业务元数据和历史；Chroma 保存 chunks、向量和 metadata；文件系统保存上传文件及运行目录。三者必须使用同一运行环境的配置，不能跨环境共享 active generation 元数据。

## 本轮 Harness 证据（2026-10-18）

固定三篇论文、同一模型，比较原有问答 A、固定检索 B、Harness C，覆盖事实、三论文比较、无答案三道题。九组最终记录中八组返回文本或报告，一组供应商 429 失败，返回结果包括一组部分完成报告。

三论文比较题中，A/B/C 的来源覆盖为 1/2/3 篇，模型请求为 3/1/8 次，耗时约 178/66/441 秒。结果表明该样例中反馈检索扩大了文档覆盖，同时增加调用与等待；不代表整体准确率提升，也未逐条核验全部引用。时间包含供应商等待、数据库检查点和限流间隔。

代码入口：`eval/runners/harness_pilot.py`。本机产物：`eval/runs/harness/h4_pilot_20261018/`，汇总为 `overview.json`。初次受实验检索上限影响的 A 组尝试已单独归档，修正后重跑 A；中断的未完成尝试不计入九组最终记录。

本轮收尾仅修改项目说明；未重跑 pytest、浏览器验收或模型实验。此前 smoke 的范围各有区别，不等同于当前全量测试通过。

## 明确限制

1. 历史 20 题的接口执行和 Judge 指标不代表本轮 Harness 效果。Harness 完成状态主要检查报告结构，结论和引用仍需回原文核验。
2. 评估集规模小，复杂表格、图片、OCR、Summary 和跨文档证据覆盖仍需扩展。
3. 尚无 10K/100K/500K chunks 的容量和并发基准。
4. 免费 Space 的本地磁盘可能因重建或休眠丢失；线上数据与本地必须隔离。
5. JWT 尚未升级到 HttpOnly Cookie、Refresh Token、吊销和 RBAC。
